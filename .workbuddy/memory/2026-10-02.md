## JWT 鉴权安全性评估（只做评估，未改代码）

用户问"后端是不是都从 JWT 里拿权限，安不安全"。查完的结论：

**现状**
- `JwtUtil.generateToken(userId, username, role)` 在登录时签发，role 取自数据库 `user.role`，
  写进 payload；`expiration: 86400000`（24 小时）
- `JwtAuthenticationFilter` 验签后从 claims 取出 `userId` + `role`，写入 SecurityContext
- Controller 一律用 `SecurityUtils.getUserId()/getRole()`，不信任前端传参
- `/logout` 是空实现（注释：JWT 无状态，前端清本地 token 即可）
- 无 token 黑名单、无 refresh、无 token 版本号

**结论：分两层**
- 安全面：payload 有签名，前端改不动 → 冒充不了别人；且**资源归属判定是回查数据库的**
  （`assertRecordVisible` 查 exam_record 比对 userId，`assertExamOwner` 比对 creatorId），
  不是"全靠 JWT"。所以越权这条是挡住的。
- 不安全面（三个真实代价）：
  1. **role 是 24 小时快照**：降级/封号后旧 token 在过期前依然有原权限；登录失败锁定只挡新登录
  2. **无法主动注销**：token 被截获后 24 小时内持续有效
  3. **密钥默认值写死在 `application.yml`**（`${JWT_SECRET:SmartExamSecretKey2026...}`），
     代码泄露 = 可以自签任意 role 的 token = 全部鉴权失效。之前加的只是启动 WARN，没强制

**建议（待用户确认是否动手）**
- 必做：密钥走环境变量/换随机值；有效期 24h → 2h
- 推荐：token 只放 userId，filter 里回查数据库拿当前 role（改一次 DB 查询换"改权限立即生效"）
  注意 filter 是 `new JwtAuthenticationFilter(jwtUtil)` 手动构造的，要改需把 UserService 也传进去
  或改成 Spring Bean
- 可做：logout 加短黑名单（内存/Redis），存到 token 自然过期为止

## 已实施：角色改为回查数据库（用户要求"最小改动"）

改动只落在 3 个文件，Controller / Service / SecurityUtils 一行没动：

1. `JwtAuthenticationFilter`：构造器多接一个 `UserService`；验签后只取 `userId`，
   然后 `userService.getById(userId)` 拿 `user.getRole()` 作为权限来源。
   查不到用户、或 role 为 null/非法 → 不写 SecurityContext → 401。
2. `SecurityConfig`：`filterChain(HttpSecurity, JwtUtil, UserService)` 加一个形参，
   `new JwtAuthenticationFilter(jwtUtil, userService)`。Spring 会自动注入 @Bean 方法的参数。
3. `JwtUtil.generateToken(Long userId, String username)` 去掉 role 形参和 role claim
   （避免留下一份没人用、将来可能被误读的陈旧快照）；`UserServiceImpl` 调用处同步改。

核对过：无循环依赖（没有任何类注入 SecurityConfig）；`user` 表是物理删除
（无 @TableLogic），所以删号后 `getById` 返回 null → 401，符合预期。

代价：**每个携带 token 的请求多一次 user 表主键查询**。白名单接口不带 Authorization 头，
会在取 header 那一步直接 return，不查库。毕业设计规模可忽略。
若要优化可加短 TTL 缓存，但那会重新引入"权限生效延迟"，不做。

**仍未做**：密钥默认值还在 yml、有效期仍是 24 小时、logout 仍是空实现（无黑名单）。

## 全量核对结论（用户问"是不是所有访问都用新 role"）

扫描结论：**是的，所有 HTTP 访问都用数据库里的新 role**。依据：
1. 全项目没有 `@PreAuthorize` / `@Secured`，权限判定唯一入口就是 SecurityConfig + SecurityUtils
2. 4 处 `getRole()` 调用（AnnouncementController / AuthController / ExamController / RecordController）
   **全部**是 `SecurityUtils.getRole()`，没有一处从请求体或参数里取
3. `ExamServiceImpl.canAccess(examId, userId, role)` 的 role 由调用方传 `SecurityUtils.getRole()`

**两个例外 / 残留**
- 定时任务 `ExamAutoSubmitTask` 没有 HTTP 请求、SecurityContext 为空 → 里面调
  `SecurityUtils.getUserId()/getRole()` 一定返回 null。现在没调，但这是长期约束。
- **登录失败锁定不进鉴权链路**：`loginAttempts` 只挡新登录，已发出的 token 在锁定期内照常可用。
  要挡得在 filter 里额外查一次锁定状态（角色之外的第二个维度）。

**顺带核对的提权防线（都是对的）**
- `UserController.update`：非超管强制 `setRole(null)` + `setId(自己)`，既改不了自己角色也改不了别人
- `UserServiceImpl.register`：`role != 0 && role != 1` 就降级为学生 → **自注册当不了超管**
- 注册页自带"学生/教师"二选一是前端有意做的（非漏洞），超管只能由超管在后台创建
